# Build orders

Generated by `scripts/build-index.mjs` from `assets/index.json` and every skill's frontmatter. Do not edit it by hand: change the data (or a skill's description), then run `node ${CLAUDE_SKILL_DIR}/scripts/build-index.mjs --write`.

## Contents

- Running a "done when" check
- A new app from an empty repo
- A new feature
- A release to the App Store and Google Play
- Adopting the skills in an existing app
- A new game (games plugin)

Each layer is tested before anything depends on it. A step starts only when the step before it passes its "done when" checks. Every step is test-first (tdd-workflow) and ends in a commit and a short report (git-commits-and-reporting).

## Running a "done when" check

Run every "done when" command from the repo root as `node <that skill's folder>/scripts/<script>.mjs . <options>`: the repo root is the first argument, never `--root`. A skill in brackets after a command owns the script. A line `SKIP <file> [<rule>] not yet created (<skill> creates it)` names a file a later step creates; it is expected until that step and a failure after it. `NOT APPLICABLE: <fact>` means a repo fact puts the whole check out of scope (the package is not installed). Exit 2 is never a pass.

## A new app from an empty repo

The skeleton holds only what its own configs and gates need, so every gate is green on day one; each later step adds the layer the next one depends on. Each skill's checker reports its part as missing until its step: that is the order, not a bug. When the repo is a monorepo, each skill's "When multi-package" section applies.

### When `npm run verify` is green

`npm run verify` (quality-gates' runner) runs its steps in order and stops at the first red one. On an app built in this order a gate is expected red only before its "Green from" step, for the reason given, and that is not a failure of the step in progress: run the other gates one by one meanwhile and name the pending gate in the report. Any other red gate is a real failure of the step that turned it red. test:sim joins verify only when the first *.sim.test.ts exists (games plugin), and a gate another skill appends to quality-gates.json "verifyExtraSteps" is green from the step that adds it.

| Gate | Green from | Red before that because | Run meanwhile |
|---|---|---|---|
| format:check, lint, typecheck | step 1 | never expected red: every template is Prettier-clean and compiles where its step puts it (check-index proves the order import-closed) | - |
| i18n:verify | step 5 | scripts/i18n/verify-catalogs.ts does not exist yet (MODULE_NOT_FOUND): i18n-strings-and-catalogs copies it with the first catalogs, so verify stops here and the later gates do not run | `npm run -s check:fast`, `npm run -s lint`, `npm run -s typecheck`, `npm run -s test:coverage`, `npm run -s check:unused`, `npm run -s audit:licenses` and `npm run -s check:deps`, one by one; check-gate-wiring names the script as not yet created |
| check:unused, guardrail, test:coverage | step 1 | never expected red: every copied file brings its test in the same step, so coverage holds after every step; they run inside verify from step 5 | - |
| export:audit, audit:licenses, check:deps | step 1 | never expected red (an Expo patch younger than the release-age window is a dated WARN, dependency-management); they run inside verify from step 5 | - |

### What each step copies, installs and generates

The build-order contract: at each step, copy exactly these templates (tests included), install exactly these packages, and run the named tool for the generated files. A path is the repo path written on line 1 of a template (or its path under `templates/`) in the named skill; a glob takes every such template of that skill that no earlier step copied. Every import of a copied file resolves to a file copied or generated at that step or earlier, every npm package it imports is installed by then, and every file brings its test in the same step, so `tsc`, `check:fast` and `test:coverage` stay green after every step: `check-index.mjs` (rule `step-import-closure`) proves it on the library. When a copy fails to compile, the manifest is wrong: report it, never fetch files by following tsc errors.

## A release to the App Store and Google Play

From a green main branch to builds in TestFlight and a Play testing track, on EAS Build and Submit (eas-build-and-submit owns the store sequence). Every check that reads configuration baked into the binary (variants, eas.json profiles, the update channel and runtime version, the crash reporter's source-map upload) runs at step 4, before anything is built, so a FAIL never costs a build number. A team without EAS takes the local lanes instead: `npm run release:ios` (ios-release-testflight) and the local Play upload (android-release-play), each behind the same artifact gates; the steps that carry a local-lane proof say what it runs instead (step 4 runs `check-eas-config.mjs .` without --release, which prints NOT APPLICABLE or the internal-only EAS note), and those skills' local-lane commands replace steps 5 to 8. Ship gates never skip: their only relaxation is a keyless --rehearsal, which is never release evidence. Stop and ask the developer before the store build, every submission, every tag push and every rollout change.

### What each step copies, installs and generates

The build-order contract: at each step, copy exactly these templates (tests included), install exactly these packages, and run the named tool for the generated files. A path is the repo path written on line 1 of a template (or its path under `templates/`) in the named skill; a glob takes every such template of that skill that no earlier step copied. Every import of a copied file resolves to a file copied or generated at that step or earlier, every npm package it imports is installed by then, and every file brings its test in the same step, so `tsc`, `check:fast` and `test:coverage` stay green after every step: `check-index.mjs` (rule `step-import-closure`) proves it on the library. When a copy fails to compile, the manifest is wrong: report it, never fetch files by following tsc errors. It starts from a repo that has passed steps 1 to 18 of "A new app from an empty repo".
