# The src/ layout and where every file goes

The canonical layout of one Expo app, what each folder holds, the rules for route files, the placement
table, and the recipes for adding a feature, a folder or a new kind of file. Read this before creating
any file whose home is not obvious. A new kind of file gets a row here in the same change.

## The tree

```
<repo>/
  app.config.ts          the only app config; Node runs it (type stripping)
  package.json           "main": "expo-router/entry"
  tsconfig.json          "paths": { "@/*": ["./src/*"], "@/assets/*": ["./assets/*"], "@test/*": ["./test/*"] }
  jest.config.js         moduleNameMapper: '^@/assets/(.*)$' first, then '^@/(.*)$' (Jest takes the first match;
                         without its own '@/' keys, jest-expo maps tsconfig.json paths in their order)
  assets/<kind>/         images/, fonts/, sounds/: required as require('@/assets/<kind>/<file>')
  modules/<name>/        local Expo modules (npx create-expo-module --local), imported only by their adapter
  src/
    app/                 Expo Router route files ONLY: _layout.tsx, index.tsx, (group)/, [id].tsx, +not-found.tsx;
                         server code: api/<name>+api.ts (API routes) and the root +middleware.ts
    features/<feature>/  <feature>-screen.tsx · use-<feature>-model.ts · components/ · pure logic .ts · tests beside them
    ui/                  shared presentational components (AppText, buttons, rows, dialogs, icons)
    hooks/               shared cross-feature hooks (use-is-app-active.ts, use-window-class.ts)
    canvas/              the canvas kit (skia-canvas-rendering: canvas-layout.ts, canvas-types.ts, timeline/)
    theme/               tokens, theme sets, ThemeProvider, makeStyles, motion; global.css (web) imported by the theme
    core/                pure domain: no React, React Native, Expo or Skia imports
    services/            the composition root (services-context.tsx, create-device-services.ts, create-test-services.ts,
                         and create-root-kits.ts, the optional kits' registry)
      <concern>/         <concern>-port.ts · <library>-<concern>-adapter.ts · fake-<concern>.ts (+ tests)
    stores/              Zustand store factories, reducers, selectors
    data/                SqlDriver, repositories, migrations, the device opener (open-device-database.ts)
    api/                 ApiClient, query keys, request/response schemas
    i18n/                catalogs, intl setup, polyfills, direction
    config/              neutral config (app-variant.ts, environment, feature flags)
    games/<game>/        the games plugin: rules/ and levels/ (pure), sim/, geom/, board/
    server/              (when API routes share helpers) server-only code, recorded in srcFolders and serverFiles
    test-only.ts         the test-only gate (debug-menu-and-test-hooks owns it), with test-only-entry.ts
    test-only-entry.ts   and the entry it requires outside production
  test/                  test helpers (makeTask, renderWithProviders, renderRouterWithProviders), integration tests that need Node
  __mocks__/             root mocks for vendor SDKs that crash when Jest imports them
  scripts/<area>/        Node tooling: <verb>-<noun>.ts, run by Node type stripping
  plugins/               local Expo config plugins: with-<capability>.ts (default export)
  contracts/             architecture.json and the other repo-owned contracts the skills read
  .maestro/              E2E flows
```

`ios/` and `android/` are generated by `npx expo prebuild` (Continuous Native Generation) and
git-ignored; the checkers never read them, nor any installed skill folder (`.agents/`, `.claude/`,
`skills/`, any folder that holds a `SKILL.md`).

## What each folder holds

| Folder | Zone | Holds | May import (what the checkers enforce) |
|---|---|---|---|
| `src/app/` | routes | route files that render a feature screen; layouts mount providers | features, ui, theme, i18n, config, core; a route other than a `_layout` never imports stores, data, api or services (layouts mount the composition root and providers) |
| `src/app/**/*+api.ts`, `src/app/+middleware.ts`, contract `serverFiles` (`src/server/**`) | server | API routes, the middleware and their helpers: server code, never in the native bundle | core, api, config, data, port types, other server files, `expo-server`, `expo-router/server`, Node built-ins and Web APIs; never React Native or Expo runtime modules, routes, features, ui, theme, stores, games, adapters or local modules; nothing bundled imports it (`server-boundary`) |
| `src/features/<feature>/` | features | one feature: the screen (a pure view), the model hook (the only code that reads stores, services and navigation), its components and pure logic | its own folder, every shared layer, core; never another feature |
| `src/ui/` | ui | presentational components; data and callbacks arrive as props | theme, i18n, config, core, port types; never stores, data, api, other services files or a feature |
| `src/theme/`, `src/services/`, `src/stores/`, `src/data/`, `src/api/`, `src/i18n/`, `src/config/`, `src/hooks/`, `src/canvas/` | shared layers | tokens and theme plumbing · ports, adapters, fakes, services over ports (an error net with no SDK needs no triple) and the composition root · store factories, reducers, selectors · the SQL driver, repositories, migrations, the device opener · the ApiClient, schemas, query keys · catalogs, formatters, direction · neutral config · shared cross-feature hooks · the canvas kit | each other and core; never a feature. Adapters only from the composition root (and `src/data` its own driver; the device opener `src/data/open-device-*.ts` is part of the composition root); fakes only from tests; a `src/config` file Node code imports stays neutral |
| `src/core/` | core | pure domain types and functions | `src/core` only |
| `src/games/<game>/` | games | the games plugin | its own folder, core, ui, theme, i18n, canvas, port types and the `gameFacing` seam; never another game. `rules/` and `levels/`: only core and their own rules and levels |
| `src/test-only.ts` | src (a shared layer) | the gate | its entry, through `require()` behind the production comparison |
| `assets/` | none (not code) | images, fonts, sounds, videos | nothing; code requires them through `@/assets/` |
| `modules/<name>/` | native-module | a local Expo module (Swift, Kotlin and its TypeScript entry) | its own world; only an adapter in `src/services/<concern>/` (or `src/data/`) imports it, through `@/modules/<name>` (`vendor-sdk`) |

"Shared layers" in the rules means every zone between features and core: ui, theme, services, stores,
data, api, i18n, config. The checkers let shared layers import each other (the cycle rule keeps those
imports acyclic); the usual direction inside them is services and stores over data and api, everything
over core. Every zone's package imports follow the SDK rules (dependency-zones.md).

## Route files are routes

Expo Router turns **every** `.ts`, `.tsx` and `.js` file under `src/app/` into a route and pulls it into
the bundle through one `require.context`. On iOS and Android that context leaves out only `+api` files,
`+html` and `+middleware`; `+native-intent` ships, because the native app runs it (expo-router 57.0.24,
`_ctx.ios.js` and `_ctx.android.js`, read on 2026-10-03; the separate `_ctx-shared.js`
`EXPO_ROUTER_CTX_IGNORE` list, which drops `+api`, `+html` and `+native-intent`, is not the native one).
Verified on 2026-10-03 (Expo SDK 57, `APP_VARIANT=production npx expo export --platform ios`, then
`--platform android`): a `src/app/index.test.tsx` shipped in both production Hermes bundles, test code
included, and a `src/app/helpers/format-title.ts` shipped in the iOS bundle. So:

- A route file default-exports its component and renders a screen from `src/features/`; the thinnest
  route is one line, `export { SettingsScreen as default } from '@/features/settings/settings-screen';`. A
  route without a default export is reported (`route-file`), and Expo Router warns "missing the required
  default export".
- A route renders a screen: it imports something from `src/features/` (or a `nonFeatureScreens` file, or
  test-only code through the gate), or it only redirects (`<Redirect href="/tasks" />` from `expo-router`).
  It calls no `useState`, `useReducer`, `useEffect`, `useLayoutEffect` or `useFocusEffect`, and no other hook
  except router hooks from `expo-router` and hooks it imports from `src/features/`: `useQuery`, `useMemo`, a
  shared hook from `src/hooks/`, a translation hook or a hook written in the route file is screen logic, and
  it goes to the feature's model hook (a static screen title goes on `<Stack.Screen>` in the group's
  `_layout`; a translated title the model already holds may be set with `<Stack.Screen options>` inside
  the thin route, as screen-contracts and scaffold-feature-screen do). The feature's model hook reads
  and parses the router params (`<feature>-params.ts`; navigation-and-routing: the model hook is the
  only code that reads navigation). `route-thin` tolerates a `useLocalSearchParams()` call in a route,
  but scaffold-feature-screen's `params-in-model` rule fails it.
  `+not-found`, `+html` and `+native-intent` need no feature (`route-thin`). The SDK 57
  template's `explore.tsx` and `index.tsx` hold their whole screen inline: move each into a feature when
  adopting this layout.
- Tests of a screen and its model hook live beside them in `src/features/<feature>/`. A route test (a
  link press, a deep link, a protected-group redirect, back) lives in the feature too, as
  `src/features/<feature>/<feature>-navigation.test.tsx`: it imports the route files' default exports
  (`import TasksRoute from '@/app/index'`) and renders them with `renderRouterWithProviders` from
  `@test/render-router-with-providers`, never Expo Router's `renderRouter` directly (unit-and-component-tests
  owns the helper and the route-test rules). A route file needs no test beside it: the route test that
  renders its default export covers it, or it carries `// device-only: covered by <flow>`. A test, or a
  helper in `src/app/__tests__/`, is reported (`route-file`).
- Hooks, components, stores and helpers never sit in `src/app/`, not even in a subfolder.
- A route other than a `_layout` imports no store, `src/data`, `src/api` or service (`route-thin`); its
  feature's model hook does that. Layouts mount providers (the composition root, the theme) and the
  navigator.
- Nothing but a test imports a route file (`route-leaf`): shared code moves to the feature or `src/ui`.
  A route test imports route files on purpose; `route-leaf` and ESLint's zone block both leave tests out.

Re-verify on a new SDK: read `node_modules/expo-router/_ctx.ios.js` and `_ctx.android.js`, put a file
with a unique string in `src/app/`, run `APP_VARIANT=production npx expo export --platform ios` (and
`--platform android`), and search the `.hbc` file for the string (`LC_ALL=C grep -a -c <string> dist/_expo/static/js/ios/*.hbc`).

## Server code: API routes and middleware

Expo Router API routes are files named `<name>+api.ts` anywhere under `src/app/` (`src/app/api/tasks+api.ts`
answers `/api/tasks`); they export `GET`, `POST` and the other HTTP methods and run on a server (EAS
Hosting or another WinterCG host), never on the device. The one `src/app/+middleware.ts` (root level only)
runs before every server request; on SDK 57 it runs only with `unstable_useServerMiddleware` set in the
`expo-router` config plugin (stable, without the flag, from SDK 58; verified on 2026-10-03 at
docs.expo.dev/router/web/middleware). The native `require.context` regex leaves `+api` (at any depth),
`+html` and `+middleware` out (expo-router 57.0.24, `_ctx.ios.js` and `_ctx.android.js`, read on
2026-10-03), so the checkers put these files in a separate **server** zone:

- They may use Node built-ins and Web APIs, and import `src/core`, `src/api` (request and response
  schemas), `src/config`, `src/data`, port types, other server files, `expo-server` (`StatusError`,
  `origin`) and `expo-router/server` (`MiddlewareFunction`). They never import React Native or Expo runtime
  modules, routes, features, ui, theme, stores, games, adapters or local modules (`server-boundary`): none
  of that exists on the server.
- Nothing bundled imports server code (`server-boundary`): the app calls the route over HTTP through the
  `ApiClient` in `src/api/`, and both sides share the schemas in `src/api/`.
- The route rules (`route-file`, `route-thin`, `route-leaf`), the SDK rules, `node-builtin`, the test-only
  gate and `import-time-work` do not apply to them.
- A helper several API routes share never sits in `src/app/` (Expo Router would bundle it into the app as a
  route): put it in `src/server/` and record `"srcFolders": ["server"]` and `"serverFiles": ["src/server/**"]`
  in the contract. A `serverFiles` glob inside the routes folder is ignored for the same reason.
- Test an API route from `test/` (the root TypeScript program has Node types), never from `src/`.
- **Data loaders are out of scope for these checkers.** A `loader` export inside a route file runs on the
  server (at `npx expo export` with static output, per request with server output) and needs
  `unstable_useServerDataLoaders` in the `expo-router` config plugin on SDK 57 (verified on 2026-10-03 at
  docs.expo.dev/router/web/data-loaders). The checkers see the route file as app code, so a loader that
  reads `src/data` gets `route-thin` and one that imports `node:*` gets `node-builtin`. Keep loaders out of a
  native app's routes; a web app that adopts them records the route's import in `allowedImports` with the
  reason and hands the rest to web-support.
- The app's TypeScript program (`src/tsconfig.json`, types `jest` only) cannot type-check a route that
  imports `node:crypto` (verified on 2026-10-03, TypeScript 6.0.3: TS2591 "Cannot find name
  'node:crypto'"); excluding `app/**/*+api.ts` and `app/+middleware.ts` there leaves them to the root
  program, which passed. The canonical ESLint `RUNTIME_IMPORTS` also bans Node built-ins in these files;
  both configs belong to typescript-and-lint-rules.

## Local Expo modules

`npx create-expo-module --local` creates a module in `modules/<name>/` at the app root: autolinking reads
`package.json` `expo.autolinking.nativeModulesDir` and defaults to `./modules` (expo-modules-autolinking
57.0.13, read on 2026-10-03). The module is native code like any SDK:

- Only its adapter imports it: `src/services/<concern>/<module>-<concern>-adapter.ts` behind a port with a
  fake, like any vendor SDK. Any other bundled file that imports it, by path or by the name in its
  `package.json`, is a `vendor-sdk` problem.
- Import it through an alias, never `../../modules/...` (`parent-import`): `"@/modules/*": ["./modules/*"]`
  in the root `tsconfig.json` (the form Expo's module guide writes, `@/modules/my-module`), the same alias
  relative to `src/` in `src/tsconfig.json` (the adapter's import is type-checked there), and
  `'^@/modules/(.*)$': '<rootDir>/modules/$1'` in `jest.config.js` before `'^@/(.*)$'`.
- The checkers never read inside `modules/` (Swift, Kotlin and the module's own TypeScript).

## What check-layout checks by path

- `folders`: the children of `src/` are the canonical set plus `srcFolders` from the contract (a
  `src/assets/` folder gets its own message: assets live at the root); files directly in `src/` are only
  `app-env.d.ts`, `env.d.ts`, `tsconfig.json` and the gate files `test-only.ts`, `test-only-api.ts`,
  `test-only-entry.ts` (a stylesheet such as `src/global.css` gets its own fix: `src/theme/global.css`);
  files directly in `src/services/` are only the composition root; nothing sits directly in `scripts/`, and
  every `scripts/` area is a kebab-case noun.
- `route-file`: see above (`+api` files, `+middleware` and `+native-intent` export handlers, not a component).
- `placement`: `*-screen.tsx` only in `src/features/<feature>/` (or `nonFeatureScreens`); `*-port.ts`,
  `*-adapter.ts` (and its `.ios`/`.android`/`.native`/`.web` files), `fake-*.ts` only directly in
  `src/services/<concern>/` or in `src/data/` (the data layer keeps its driver and repository ports,
  adapters and fakes); `*-store.ts` and `*-selectors.ts` only in `src/stores/` or `src/data/`, except an OS
  mirror store; `*-reducer.ts` only in `src/stores/` (games keep
  their own engines); an import of `expo/config-plugins` only in `plugins/`, `scripts/` or
  `app.config.ts`; a test that imports `node:*` never inside `src/` (the app program has no Node types).
  Files in `testOnlyFolders` may keep a debug port and fake side by side.
- `port-triple`, `composition-root`, `import-time-work`: see ports-and-adapters.md. `port-triple` applies
  only to a `src/services/<concern>/` folder that holds an adapter: a concern with no SDK, such as the error
  net in `src/services/error-net/` (error-handling-typed-results), needs no port, adapter or fake.
- `app-entry`, `app-files`: the entry (with or without semicolons), the `@/*` alias (and `@/assets/*` →
  `assets/*` when present), `src/app/_layout.tsx`, and the Jest order: when `tsconfig.json` declares a
  folder alias beside `@/*` (`@/assets/*`, `@/modules/*`) or code requires `@/assets/...`, and
  `jest.config.js` (or `package.json` `jest`) has a `'^@/(.*)$'` catch-all, the folder's own mapping must
  come before it; when the Jest config names a jest-expo preset and maps no `@/` key itself, the folder
  alias must come before `"@/*"` in `tsconfig.json` `paths` (jest-expo maps them in that order).

ESLint enforces the folder and file **names** (kebab case, the router grammar in `src/app`); naming
rules belong to naming-conventions.

## Recipe: add a feature screen

1. Write the failing screen test first: `src/features/<feature>/<feature>-screen.test.tsx`, rendered
   through the test wrapper with `createTestServices({ ... })`, querying by role.
2. Create `<feature>-screen.tsx` (a pure view taking props or the model's result) and
   `use-<feature>-model.ts` (reads `useServices()`, stores through selectors, navigation).
3. Add the route: `src/app/<segment>.tsx` default-exports a component that renders the screen and
   nothing else. The model hook reads and parses the params (`useLocalSearchParams()` through the
   feature's `<feature>-params.ts`), never the route.
4. Shared pieces move down, never sideways: a component two features need goes to `src/ui`, a rule to
   `src/core`, state to `src/stores`.
5. Run both checkers.

## Recipe: add a folder or a new kind of file

1. Look for an existing home in the table above; most "new kinds" are a feature file or a `src/core` area.
2. If none fits, stop and ask the developer: a new top-level `src/` folder is an architecture decision.
3. Once approved: add the name to `srcFolders` in `contracts/architecture.json`, add a row to this
   table's copy in the app's own docs if it keeps one, and add any import restriction to
   `eslint.config.mjs` (typescript-and-lint-rules, with a `Gate-Change:` trailer). A recorded folder is a
   shared layer (it never imports a feature). `src/hooks/` and `src/canvas/` are canonical already
   (shared cross-feature hooks, skia-canvas-rendering's canvas kit) and need no entry.

## Moving folders, app/ at the root, React Navigation

- Every folder comes from check-lib's layout: `rn-skills.config.json` can set `srcDir`, `routesDir`,
  `servicesDir` and the other keys (contract-and-config.md); the checkers then follow, and so do the
  `{servicesDir}`-style globs in the contract.
- Expo Router also accepts `app/` at the repo root. When `src/app` does not exist and `app/` does, the
  checkers treat `app/` as the routes folder.
- With React Navigation's static API (the fenced alternative), there is no routes folder: `main` points
  at an `index.ts` that imports and calls `registerRootComponent(App)` once, and the navigator lives in a
  recorded folder. A recorded folder is a shared layer, and a navigator renders feature screens, so the
  contract records three things (a decision for the developer, rule 13):

