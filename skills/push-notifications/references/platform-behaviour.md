# iOS and Android behaviour

What the two platforms do with permissions, tokens, channels and delivery, and what that means for
the code. Facts marked (source) were read in expo-notifications 57.0.21 on 2026-10-14; (docs) come
from docs.expo.dev for SDK 57 or the platform documentation; (both) from both. Re-verify with
`npm view expo-notifications@~57.0.21 version` and the docs page `versions/v57.0.0/sdk/notifications`.

## 1. The permission

| | iOS | Android 13+ (API 33+) | Android 12L and older |
|---|---|---|---|
| Prompt | once per install; after a refusal only Settings can turn it on | `POST_NOTIFICATIONS` runtime prompt; after a second refusal no prompt | none: notifications are on unless the person turns them off |
| Before the prompt | `undetermined` | `undetermined` (status `undetermined` or `denied` with `canAskAgain`) | `granted` |
| After "no" | `denied`, `canAskAgain: false` → **blocked** | first time `denied` + `canAskAgain: true`; second time **blocked** | — |
| Quiet start | `allowProvisional`: delivered silently to Notification Center without a prompt; status `PROVISIONAL` (3) → `'provisional'` | — | — |
| Precondition | — | a channel must exist before a token is issued (Expo's docs); with targetSdk 33+ the prompt shows when the app calls `requestPermissionsAsync`, while an app targeting 12L or lower gets the system prompt only after its first channel exists (Android docs); the library manifest declares `POST_NOTIFICATIONS` (source) | — |

Provisional is a start, not the end: `requestPermissionsAsync()` on a provisional app shows the full
prompt, so `optInToPush` asks again when the person taps an in-context "Notify me" while delivery is
only provisional (an upgrade to banners and sound); a refusal there turns quiet delivery off too
(`'declined'`, and the next sync unregisters). The launch and foreground syncs never ask.

Consequences in the code: `optInToPush` creates the channels first; `'blocked'` is its own outcome so
the screen offers `Linking.openSettings()` instead of a button that does nothing; the permission is
read (never requested) at launch and on every return to the foreground, because the person may change
it in Settings at any time; and `usePushSync` starts each registration sync only after the latest
channel sync settled, because Android issues no token before a channel exists (Expo's docs:
`setNotificationChannelAsync` must be called before `getDevicePushTokenAsync` or
`getExpoPushTokenAsync`) and on 12L and older the permission is already `granted` at the first launch. The pre-prompt explanation screen is permissions-and-system-prompts'
pattern; this skill decides *when* push asks: after an action whose value the notification extends
("Tell me when they add tasks" right after sharing a list), never at launch, never in an onboarding
carousel before the person has used the app.

Apps targeting Android 13+ (the canonical targetSdk is 36) decide themselves when the prompt shows;
creating channels at launch shows nothing. An app targeting 12L or lower would get the system prompt
the moment it creates its first channel.

## 2. Tokens

| | iOS | Android |
|---|---|---|
| Device token | APNs token (hex), from `getDevicePushTokenAsync()` | FCM registration token |
| Needs | the `aps-environment` entitlement (expo-notifications plugin, `mode`), a provisioning profile with Push | `google-services.json` in the build (`android.googleServicesFile`); without it no token |
| Expo token | `getExpoPushTokenAsync({ projectId, devicePushToken })` posts the device token to Expo's server: it fails offline (`ERR_NOTIFICATIONS_NETWORK_ERROR`) (source) | same |
| Changes when | reinstall, restore to a new device, sometimes OS updates | reinstall, app data cleared, restore, token refresh by Firebase |
| Rotation event | `addPushTokenListener` fires while the app runs (docs: "may be changed by the push notification service while the app is running") | same |

- `projectId` resolution inside `getExpoPushTokenAsync` (source): `options.projectId`, else
  `Constants.easConfig?.projectId`, else `Constants.expoConfig?.extra?.eas?.projectId`; none →
  `ERR_NOTIFICATIONS_NO_EXPERIENCE_ID`. The template passes it explicitly from `readEasProjectId()`
  so a build made outside EAS fails loudly in a test, not silently on a device.
- `mode` (plugin): writes `aps-environment` into the generated entitlements, `development`
  (sandbox APNs, the default) or `production`; the template states it per variant. Expo's SDK 57
  docs: "The iOS APNs entitlement is always set to 'development'. Xcode automatically changes this to
  'production' in the archive generated by a release build", so a distribution export (EAS Build,
  TestFlight, App Store) signs with the provisioning profile's production entitlement whatever the
  config says. The Expo push service picks the APNs environment for each token by itself.
- A token is not a secret, but it is a device identifier: store forms (App Privacy "Device ID",
  Google Play Data safety "Device or other IDs") declare it (privacy-and-store-declarations).

## 3. Android channels

- Android 8+ files every notification under a channel; the person can mute, silence or re-sound each
  channel in Settings, where its **name and description** (translated: `namedPushChannels(t)`) appear.
- **Importance, sound and vibration are fixed once a channel exists** on a device; an app may change
  only the name and description afterwards (`setNotificationChannelAsync` with the same id renames).
  A new behaviour therefore gets a new id, and a channel id is never reused for something else.
- A push whose `channelId` names a channel the device never created is not shown (docs). The
  channels are created at every launch (`usePushSync`) and before the prompt (`optInToPush`).
- A push without `channelId` goes to the plugin's `defaultChannel` (FCM v1 default channel
  metadata, `com.google.firebase.messaging.default_notification_channel_id`, source); without one,
  expo-notifications uses its fallback channel, shown to the person as "Miscellaneous" (source:
  `expo_notifications_fallback_channel_name`). Keep `defaultChannel` equal to the contract's.
- Deleting a channel (`deleteNotificationChannelAsync`) leaves a "deleted channels" count in the
  app's settings page; retire ids rarely.

## 4. Delivery by app state

| App state | Notification with title/body | Data-only message |
|---|---|---|
| Foreground | the handler decides (3 s at most; none → not shown) | `addNotificationReceivedListener` only |
| Background | the OS shows it; no app JS runs | iOS: needs `content-available` (`_contentAvailable`/`contentAvailable`), `enableBackgroundRemoteNotifications: true` in the plugin (adds `UIBackgroundModes remote-notification`), throttled by iOS; Android: delivered to a task registered with `registerTaskAsync` |
| Killed | the OS shows it; a tap launches the app (`lastResponse()`) | iOS: not delivered after a force-quit; Android: usually delivered to the task |

The docs say the OS "may decide not to deliver" background data messages: never build a feature on
them (sync on the next foreground instead). Background tasks are background-tasks' subject.

## 5. Taps

- A tap on the notification body has the action id `DEFAULT_ACTION_IDENTIFIER`
  (`expo.modules.notifications.actions.DEFAULT`); the adapter maps it to `'open'`.
- `getLastNotificationResponse()` and `clearLastNotificationResponse()` are synchronous in SDK 57;
  the `*Async` forms are deprecated wrappers (source: `NotificationsEmitter.js`).
- `useLastNotificationResponse()` returns `undefined` until known, then `null` or the response: a
  hook that renders on it navigates late and twice; the router hook (`usePushTaps`) reads once.
- A tap on a notification that arrived while the app was in the foreground goes through the same
  listener as any other tap.

## 6. Badges, icons and sounds

- The badge number is iOS-only in the handler (`shouldSetBadge`); Android launchers show a dot or
  count from the notifications themselves. Clear or set it with `setBadgeCountAsync` when the app
  shows the items (a decision of the app; the server sends `badge` with the count it knows).
- Android's status-bar icon (`icon` in the plugin): a 96×96 PNG, white on transparent. A full-colour
  icon renders as a white square. `color` tints it in the shade.
- Custom sounds: list `.wav` files in the plugin's `sounds`; on Android a channel's sound is fixed at
  creation (section 3).

## 7. Expo Go, simulators and emulators

- **Expo Go on Android has no remote push since SDK 53** (docs); local notifications still work.
  Use a development build. In Jest's Android environment, importing expo-notifications throws the
  same "removed from Expo Go" error, so Android adapter tests mock the module with a factory.
- **iOS simulators receive remote pushes** on Xcode 14 or later (macOS 13+, iOS 16+) (docs), and
  `xcrun simctl push <udid> <bundle-id> <file.apns>` delivers a payload without any server
  (testing-push.md). Use a named simulator UDID, never `booted`.
- **Android emulators** need a system image with Google Play services to get an FCM token (docs).
- Physical devices on both platforms are required before release (testing-push.md section 5).

## 8. Pitfalls with fixes

| Symptom | Cause | Fix |
|---|---|---|
| No permission prompt on Android 13+ | already blocked (the second refusal) or never requested from an action; with targetSdk 12L or lower, no channel created yet | show the Settings hand-off on `blocked`; ask from the press (`optInToPush`, channels first) |
| Prompt appears at launch | `requestPermission` in an effect or the root layout | ask from an action only (`permission-in-context`) |
| `ERR_NOTIFICATIONS_NO_EXPERIENCE_ID` | no project id in a non-EAS build | `extra.eas.projectId` in the app config + `readEasProjectId()` |
| Android: no token, "FIS_AUTH_ERROR" or a registration error | no or wrong `google-services.json`, or the variant's package missing from it | `android.googleServicesFile`; add every variant's package to the Firebase project (setup-and-credentials.md) |
| Push arrives but nothing shows in the foreground | no handler, or it took more than 3 s | one handler in the adapter, synchronous policy |
| Pushes stop after a while | token rotated, server kept the old one | `onTokenChange` → re-register with `previousToken` |
| Tap opens the app but not the screen | launch tap not read, or read before the navigator mounted | `usePushTaps` in the root Stack component |
| Same screen opens twice at cold start | launch response and listener both handled | dedupe by notification id (`startPushTapRouting`) |
| iOS tap data is `undefined` with a hand-made APNs payload | custom keys at the top level | put the data under `"body"` (architecture-and-contract.md section 6) |
| Android shows no heads-up for a "quiet" foreground push | `shouldPlaySound: false` hides the banner on Android | intended for quiet kinds; loud kinds play sound |
| Android status bar shows a white square | full-colour `icon` | white-on-transparent 96×96 icon |
| Push to a store build never arrives, development works | the store bundle id has no Push Notifications capability or APNs key in EAS (`eas credentials`); the server holds a token from a development build (each bundle id has its own token); or the APNs key was revoked (`InvalidCredentials` receipts) | `eas credentials` for the store bundle id (a person); register from the store build itself; upload a new key (setup-and-credentials.md section 4) |
| Next person on the phone gets the last person's pushes | no unregister at sign-out | `push-registration` server sign-out step |
| `MessageTooBig` receipts | payload over 4096 bytes | ids in data, fetch content after the tap |
