# Checking a library against the New Architecture

How to tell whether a native package runs on the New Architecture natively, what to do when it does
not, and the decisions file that records it. Verified on 2026-10-14: Expo's New Architecture guide
(docs.expo.dev/guides/new-architecture), the React Native 0.82 release post, and the installed <!-- stack-pin-ignore: the release that changed it -->
React Native 0.86.3 and Expo SDK 57 packages of the reference app. Re-verify the interop facts with
`ls node_modules/react-native/React/Fabric/Mounting/ComponentViews/LegacyViewManagerInterop` and
`grep -n RCT_REMOVE_LEGACY_ARCH node_modules/react-native/scripts/react_native_pods.rb`.

## 1. Where the platform stands

- **Expo SDK 55 and later run only on the New Architecture**; `newArchEnabled: false` is ignored
  (remove it; expo-sdk-upgrade's `removed-config` rule fails while it is written). Expo Go supports
  only the New Architecture. Every `expo-*` package and every module written with the Expo Modules
  API supports it.
- **React Native 0.82 made the New Architecture the only one.** Its release post says the interop <!-- stack-pin-ignore: the release that changed it -->
  layers stay "for the foreseeable future", that the classes they need "won't be removed anytime
  soon", and that removing the legacy architecture's code starts in later versions.
- **What React Native 0.86.3 still ships** (read in the installed package): the Fabric interop for
  legacy view managers (`React/Fabric/Mounting/ComponentViews/LegacyViewManagerInterop`), the
  TurboModule interop feature flag (`useTurboModuleInterop`), and `Libraries/BatchedBridge/NativeModules.js`.
  On iOS, `react_native_pods.rb` sets `RCT_REMOVE_LEGACY_ARCH=1` unless it is set to `0`, so the
  legacy architecture's own code is compiled out while the interop layers remain.

So a library written for the old architecture still works today *through the interop layer*, with its
limits (no synchronous calls, view managers wrapped in an adapter, events through the old emitter),
and with an announced end. That is a decision to record, not a default.

## 2. Classifying a package from what it ships

`check-native-libraries.mjs` finds each package the way Node does (`node_modules/<package>` in the
app's folder, then in each ancestor up to the repo root) and classifies it:

| Kind | Evidence in the package | Meaning |
|---|---|---|
| `expo-module` | `expo-module.config.json` | an Expo module: New Architecture by construction |
| `new` | `codegenConfig` in `package.json` | a Turbo Module and/or Fabric component: codegen-generated, native on the New Architecture |
| `nitro` | `nitro.json`, or `react-native-nitro-modules` in `dependencies` or `peerDependencies` | a Nitro module: JSI hybrid objects generated by nitrogen, which run only on the New Architecture (react-native-mmkv 4.3.2, react-native-vision-camera 5.2.3; `react-native-nitro-modules` itself carries `codegenConfig`) |
| `interop` | a `*.podspec` (root, `ios/` or `apple/`) or `android/build.gradle(.kts)`, but none of the above | legacy architecture code; runs only through the interop layers |
| `js` | no native code | nothing to check |

What the reference app's tree looked like on 2026-10-14 (`npx expo-modules-autolinking
react-native-config --platform ios`): every direct native dependency was an Expo module or carried
`codegenConfig` (Sentry 7.11.0, Skia 2.6.2, Reanimated 4.5.1, Worklets 0.10.1, Gesture Handler 2.32.0,
Screens 4.26.2, Safe Area Context 5.7.0, Keyboard Controller 1.21.9, Google Mobile Ads 17.2.0, Audio
API 0.13.6); FlashList 2.0.2 ships no native code. One transitive package runs on the interop layer:
`@react-native-masked-view/masked-view` 0.3.2 (Objective-C and Java view managers, no codegen),
installed by `expo-router` 57.0.24 and listed in Expo's SDK 57 `bundledNativeModules.json`.

The classification is a heuristic. Its known blind spot: a package that installs a JSI host object
from a legacy module (some older JSI libraries, before Nitro) has no `codegenConfig` and no Nitro
marker, yet is not an ordinary bridge module. The decisions file overrides it with
`"architecture": "new"` and the evidence (the package's own New Architecture statement, a dev build
that used it).

**Which dependencies count.** `library-legacy` checks `dependencies` (and `optionalDependencies`):
the code the app ships. A `devDependency` classified `interop` is printed as a `note:` and not failed,
because test tooling such as an end-to-end runner ships an `android/` folder it adds to the test build
itself (detox 20.51.4: `android/build.gradle`, no podspec, no `ReactPackage`, so autolinking links
nothing). Expo autolinking does traverse top-level `devDependencies` (expo-modules-autolinking
57.0.13, `dependencies/resolution.js`), so a runtime module listed there by mistake would still be
linked: move it to `dependencies`, where the rule sees it. Transitive notes (section 7) follow the
runtime dependencies only.

**When multi-package.** In an npm-workspaces repo, run the check once per app, on the folder holding
that app's `package.json` (`node ${CLAUDE_SKILL_DIR}/scripts/check-native-libraries.mjs apps/<app>`).
Hoisted packages are found in the ancestor `node_modules` folders up to the repo root (the first
folder with `.git`, or a `package.json` with `workspaces`), and each transitive package is resolved
from its parent's folder, as Node resolves it; the decisions file and the expo-doctor config are the
app's own (`apps/<app>/contracts/native-libraries.json`, `apps/<app>/package.json`).

## 3. The workflow before adding a native package

1. Is there an Expo SDK package for it? (`npx expo install expo-<x>`; decisions.md section 1.)
2. Read the package on React Native Directory (reactnative.directory): its New Architecture field,
   last release, platforms, and whether it is unmaintained.
3. Install it with dependency-management's procedure (the version table, the release age, the
   install-script review), in a branch.
4. Run `node ${CLAUDE_SKILL_DIR}/scripts/check-native-libraries.mjs .` and `npx expo-doctor`.
5. `interop` → section 5. `new` or `expo-module` → build a dev client on a named iOS simulator and
   Android emulator and exercise the screens that use it.

## 4. expo-doctor and React Native Directory

`npx expo-doctor` checks the app's dependencies against React Native Directory and warns about packages
that are unmaintained, untested or incompatible with the New Architecture, and (by default) about
packages the directory does not list. Configure it in `package.json`:

```json
{ "expo": { "doctor": { "reactNativeDirectoryCheck": {
  "enabled": true,
  "exclude": ["react-native-legacy-picker"],
  "listUnknownPackages": true
} } } }
```

- `enabled: false` (or `EXPO_DOCTOR_ENABLE_DIRECTORY_CHECK=0`) switches the check off: `doctor-check`
  fails it in `package.json`. Keep the variable out of CI and `eas.json`.
- `exclude` accepts names and `/regex/` patterns. Every excluded name needs a decisions-file entry,
  and a pattern is refused (`doctor-check`): it silences packages that do not exist yet. A package
  that is native on the New Architecture but excluded (for example a private package the directory
  does not list) gets `"architecture": "new"` with the reason for the exclusion as its evidence.
- `listUnknownPackages: false` only hides "not in the directory" warnings for private packages.
- Run expo-doctor without `-s` and with the network (dependency-management documents the
  `npm_config_loglevel=silent` trap).

## 5. When a package runs only on the interop layer

In order of preference:

1. **Replace it**: an Expo SDK package, a maintained fork with `codegenConfig`, or a
   New-Architecture-native alternative from React Native Directory. Expo's guide lists common
   replacements (for example `rn-fetch-blob` → `react-native-blob-util`, `react-native-fs` →
   `expo-file-system`, `react-native-geolocation-service` → `expo-location`); run the classification
   on the replacement too before switching.
2. **Wrap what you need in a local Expo module** when the package wraps a native SDK you could call
   directly: often a few Swift and Kotlin functions (decisions.md, expo-modules-api.md).
3. **Keep it, deliberately**: test every screen that uses it on an iOS simulator and an Android
   emulator (layout, events, accessibility), then record the decision (section 6) with a recheck date.
   Every Expo SDK move is a recheck as well.

## 6. contracts/native-libraries.json

```json
{
  "libraries": {
    "react-native-legacy-picker": {
      "architecture": "interop",
      "decision": "keep",
      "reason": "The due-date wheel picker; no New Architecture picker matches its accessibility yet",
      "evidence": "React Native Directory: newArchitecture false (2026-10-14). Due-date screen tested on the iOS 26.5 simulator and an Android 16 emulator",
      "recheckBy": "2027-01-14"
    }
  }
}
```

| Rule | Fails when |
|---|---|
| `library-legacy` | a dependency (`dependencies`, `optionalDependencies`) classified `interop` has no entry |
| `library-entry` | a field is missing or empty, `architecture` is not `interop`/`new`, `decision` is not `keep`/`replace`, `replace` has no `replaceWith`, or `recheckBy` is not a date |
| `library-stale` | the package is not a direct dependency, ships no native code, or now runs natively: an Expo module, `codegenConfig` or a Nitro module (delete the entry) |
| `library-recheck` | `recheckBy` is before today (`--today` pins the date in tests) |
| `doctor-check` | the directory check is off, or excludes a package without an entry, or a pattern |

The file is the app's; the template in `templates/contracts/` starts it empty with its JSON schema.

## 7. Transitive packages

A native package another package installs (masked-view under expo-router) is that package's choice.
The checker prints it as a `note:` line with its parent and does not fail: the app cannot pin it away,
and the parent (here an Expo SDK package) owns its compatibility. Watch the note across SDK moves.

## 8. Symptoms of an interop-only package

- A view renders in a wrapper and ignores some props or layout (the Fabric interop adapts the view
  manager's props).
- A method that was synchronous on the old bridge returns a Promise or nothing.
- A red box or a log line naming the interop layer or "unimplemented component" for a view the
  library registers under its old name.
- The library's issue tracker has an open "New Architecture" issue: the best evidence for the entry.
