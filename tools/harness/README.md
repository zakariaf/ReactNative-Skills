# tools/harness: the reference Expo app

The harness is a small, real Expo SDK 57 app and the reference app every finished skill agrees with:
the `default@sdk-57` template (Expo Router, `src/app/`, typed routes, React Compiler, the `@/*` alias)
reduced to one neutral Tasks screen, with the whole canonical stack installed, every canonical file of
`tools/shared/repo-templates/` in place (root configs, `.npmrc`, `.claude/settings.json`, the canonical
contracts, `__mocks__/`, `src/`, `test/`, `scripts/`, `design/`), and the templates of the finished
skills wired together the way an app adopts them, each listed in `adopted.json`. It exists to prove
templates. `node tools/verify-templates.mjs <skill>` copies a skill's templates into a temp copy of
this app and runs the same gates an app runs: a template that fails here does not ship (DECISIONS §8).
The skills' own checkers run against this folder too (the table in
[Skill checkers](#skill-checkers-on-the-harness-2026-10-17)).

## Install

```sh
npm ci --prefix tools/harness      # about 20 s on a warm cache; node_modules is git-ignored
```

`.npmrc` (the canonical file) sets `engine-strict=true`, `strict-allow-scripts=true` and
`min-release-age=7`, so npm must satisfy `engines` (Node ≥ 22.18, npm ≥ 11.17.0; Node 26.4 ships npm
11.17), every install script in the tree must be reviewed in `package.json` `allowScripts`, and no
release younger than 7 days installs. On a CI image with an older npm, run
`npm install -g npm@11.17.0` first. A second installed copy elsewhere (for example a fast local clone)
works too: point `--harness <dir>` or `RN_SKILLS_HARNESS` at it.

### The one deliberate red row

design-review-workflow's `check-signoff` is a release gate: it passes only when the version in
`package.json` (1.0.0) has a signed-off end-of-build design review, which needs the sweep captured
on a simulator and an emulator and a person's device pass. It has no SKIP and no NOT APPLICABLE on
purpose, so on the harness it prints `FAIL design-review [signoff-missing] no design review of
version 1.0.0` and exits 1, and it will until someone runs a real review on devices. That is the
only red row, and it is expected. CI therefore never runs it on the harness: the harness's own
`ci.yml` runs `npm ci` and `npm run verify` (the gates in `quality-gates.json`, none of them a skill
checker), and a repository-level workflow that sweeps the skill checkers over `tools/harness` must
leave `design-review-workflow/scripts/check-signoff.mjs` out (or allow its exit 1), exactly as an app
runs it only at release time.

## verify-templates

```sh
node tools/verify-templates.mjs <skill...> [--harness <dir>] [--only <glob>] [--keep]
                                [--no-jest] [--no-lint] [--no-prettier] [--sync-harness]
node tools/verify-templates.mjs                  # the harness drift check alone (no install needed)
node tools/verify-templates.mjs --sync-harness   # copy the canonical files, refresh the adopted copies
```

For each skill it clones the harness source (APFS clone where the volume allows it) without
`node_modules` into a temp folder, symlinks `node_modules` to the installed harness, lays the canonical
files from `tools/shared/repo-templates/` over it, copies the templates, and runs:

1. `tsc --noEmit` for both programs (`tsconfig.json`, `src/tsconfig.json`), without incremental files;
2. ESLint `--max-warnings 0` on the copied files;
3. Prettier `--list-different` on the copied files that needed no placeholder value;
4. Jest `--findRelatedTests` on the copied files (their own tests and any harness test that imports
   them, unit and golden projects), and `jest.sim.config.js` for copied `*.sim.test.ts`.

**Canonical files.** The root configs listed in `CANONICAL_FILES` (with `dot-npmrc` → `.npmrc`,
`dot-claude/settings.json` → `.claude/settings.json` and `contracts/{contrast,contrast.schema,
dependency-policy}.json` and `metro.config.js`), every root mock in `repo-templates/__mocks__/`, and every file under `src/`,
`test/`, `scripts/` and `design/` in repo-templates (`CANONICAL_TREES`, discovered at run time). A path
that holds a placeholder (`__NAME__`) is a template to be filled, not an app file, and is left out. The drift
check compares each with the harness copy byte for byte (`knip.json` without the harness keys
`ignoreDependencies`, `ignoreBinaries`, `ignoreIssues`), `--sync-harness` copies them (keeping those
keys), and every temp app gets them laid over the clone.

**Adopted templates.** `adopted.json` lists every harness copy of a skill template. The drift check
fills the template's placeholders from the skill's `assets/template-placeholders.json` and fails
(`harness-adopted`) on a copy that differs and is not marked `adapted`, a missing copy, a template that
no longer exists, a key that is not the path the template lands at, a canonical path listed as
adopted, an `adapted` entry that equals its template (drop the mark so the check guards it again), and
a malformed entry. `--sync-harness` rewrites every plain entry's copy; adapted copies are never
touched. A harness npm script that `package-scripts.json` lacks fails `harness-drift` unless
`"$scripts"` names it with its skill and reason (and a `"$scripts"` entry for a script that is
canonical now, or that the harness dropped, fails too).

**Placement.** Line 1 of a code template names its repo path (`// src/features/tasks/tasks-screen.tsx`,
an optional `: description` or ` — description` may follow); YAML, shell and TOML use `# <path>`
(line 2 after a `#!` line); JSON and every other file land at their path under `templates/` (a `dot-`
prefix becomes `.`). Absolute paths, `..`, `node_modules/`, an extension that differs from the
template's, and two templates naming one path are `placement` failures. A message catalog (a flat
JSON object of strings) that lands on an existing harness catalog adds its keys to it (template values
win, keys sorted) instead of replacing it: the harness keeps its own messages, as an app would.

**Placeholders.** `__UPPER_SNAKE__` names (never `__DEV__`) are replaced in paths and contents from
`<skill>/assets/template-placeholders.json`, for example `{ "__FEATURE__": "tasks" }`. A name without a
value gets a deterministic default and a `WARN` line: kebab case (`__WIDGET_NAME__` → `widget-name`),
`*_PASCAL` → PascalCase, `*_CAMEL` → camelCase, `*_CONST`/`*_UPPER`/`*_SNAKE` → UPPER_SNAKE.

**Output** follows the check-lib contract: `FAIL <skill>/templates/<file>:<line> [<rule>] <message>
Fix: <fix>`, a summary, then `RESULT: PASS` or `RESULT: FAIL (<n> problems)`. Rules: `placement`,
`tsc`, `eslint`, `prettier`, `jest`, `harness-drift` (a committed harness copy differs from
repo-templates, or the canonical `package.json` pins/scripts are not what the harness installs and
runs), `harness-adopted` (an adopted copy or the manifest is wrong), `harness-stale` (the installed
harness came from another lockfile). A problem in a file no template wrote is labelled
`harness/<path>` and says a copied template broke it (the harness alone is green). A skill without
`templates/` is `NOT APPLICABLE` (exit 0); an `--only` glob that matches no template, and no installed
harness, are exit 2 (the latter with the install command). The drift check runs before every skill
run, so a stale harness fails every skill until `--sync-harness` (and the harness gates) put it back.

**Harness choice:** `--harness <dir>`, else `tools/harness` when it has `node_modules`, else
`$RN_SKILLS_HARNESS`. The app files always come from `tools/harness` (the committed source); only
`node_modules` comes from the installed copy. Jest keeps its transform cache in
`<installed>/node_modules/.cache/verify-templates-jest`.

**Speed:** 6 to 30 s per finished skill on an idle machine (the whole app type-checks every time),
about 2 minutes while ten agents share it; `--no-jest` and `--only` make it faster.

**Results on 2026-10-16:** all 77 built skills (waves 1-5) pass (`RESULT: PASS`; run-goldens-rebaseline has no templates and prints NOT APPLICABLE), with the 262 canonical and 255 adopted files in place.

**Self-test:** `node tools/tests/verify-templates.selftest.mjs` generates a good sample skill and
planted-bad ones (type error, lint error, failing test, missing first-line path, path collision,
unformatted file), plus placeholder defaults, NOT APPLICABLE, a missing harness, drift with
`--sync-harness`, adopted copies (stale, refreshed by `--sync-harness`, adapted copies left alone, a
broken manifest, `"$scripts"`), a stale install, canonical-file discovery, the harness knip.json
layout and the catalog merge. It needs an installed harness.

## Deliberate differences from an app

- **The root kits run with no outside service.** Crash reporting has no DSN (the SDK never starts;
  a production build of the harness throws at launch until `EXPO_PUBLIC_CRASH_REPORTER_DSN` is set,
  the skill's misconfiguration check) and a fixed no for consent; analytics has no vendor
  (`sdk: "none"`, every build off); push registers with a stand-in that answers `unavailable` (no
  server, no accounts), and has no EAS project id (`EAS_PROJECT_ID`) and no `google-services.json`, so
  no device gets a token; local reminders read no rows. No harness build uploads source maps or
  symbols (no EAS Build, no `SENTRY_AUTH_TOKEN`). An app fills each with its own service, after the
  developer's go-ahead.
- **`prepare` installs no hooks here.** The harness runs the canonical
  `node scripts/hooks/install-git-hooks.ts` (every canonical script is there, with the canonical
  command, checked). The harness is a folder inside this repository, not a repository of its own, so
  on `npm ci --prefix tools/harness` the script prints `install-git-hooks: skipped: ...` and exits 0:
  outside a git repository it finds none, and in a git clone `git rev-parse --show-toplevel` names
  this repository's root, not `tools/harness` (verified in scratch folders on 2026-10-10, together
  with the top-level case, where it runs `lefthook install`). A bare `lefthook install` would fail the
  first and write hooks into this repository in the second. `build:ios:sim` is there too, outside the
  canonical list on purpose (`adopted.json` `"$scripts"`: only apps that build for the iOS simulator
  have it, and its multi-package form takes per-app arguments; ios-simulator-build checks it).
- **Install scripts denied** in `allowScripts`: `lefthook` (its postinstall runs `lefthook install` in
  the folder npm was started from, which for `npm ci --prefix tools/harness` is this repository;
  with `CI` set it does nothing; the guarded `prepare` does not change that script, so it stays
  denied: in a scratch repository on 2026-10-10 the approved script wrote lefthook's example
  `lefthook.yml` and a `prepare-commit-msg` hook into the enclosing repository; apps at the git top
  level keep the canonical `"lefthook@2.1.14": true`, which they need for the `.bin/lefthook` link
  that `prepare` and the guardrail call; quality-gates' gates-overview.md has the caveat),
  `@shopify/react-native-skia` (copies 712 MB of native libraries that
  tsc, ESLint, Jest and `expo export` never read) and `@sentry/cli` (downloads a binary used only to
  upload symbols). `unrs-resolver` and `fsevents` are approved. A prebuild of the harness would need
  Skia's script. npm 11.17 also skips the `.bin` links of denied packages, so `npx lefthook` and
  `npx sentry-cli` do not work in the harness (nothing in it calls them).
- **`knip.json` adds two harness keys**, each entry with its reason in `contracts/knip-ignores.json`
  (quality-gates' `knip-ignores` rule): `ignoreDependencies` for the pre-installed stack the app does
  not import yet and `@formatjs/cli` (resolved through `createRequire(...).resolve`); `ignoreBinaries`
  for macOS `plutil`, which `scripts/build/build-steps.ts` runs. The ten agent-folder `ignore` entries
  are canonical, with the canonical reasons. Everything
  else equals the canonical file; the drift check compares it without those keys and `--sync-harness`
  keeps them. knip may not ignore app code (typescript-and-lint-rules' `ignore-app-code`), so unused
  template API is tagged `@public` instead (two adapted motion files).
- **Expo patches younger than the release age (2026-10-17).** On 2026-10-17 `npx expo install --check`
  wanted 13 newer SDK 57 patches, but only one train was past `min-release-age=7`: expo 57.0.27 and
  its module map (all published 2026-10-06). The newest ones (expo 57.0.30 and expo-router 57.0.28 of
  2026-10-15, expo-notifications 57.0.23 of 2026-10-14, jest-expo 57.0.6 of 2026-10-12, ...) are 2 to
  5 days old, so `npx expo install --fix` would write specifiers npm refuses (`ETARGET ... No matching
version found for expo@~57.0.30 with a date before 10/10/2026`), and dependency-management forbids
  `--fix` and excludes inside the 7 days. The harness moved to expo 57.0.27's set with explicit specs
  (`npx expo install expo@~57.0.27 expo-auth-session@~57.0.14 expo-constants@~57.0.21
expo-linking@~57.0.12 expo-notifications@~57.0.22 expo-router@~57.0.25 expo-sqlite@~57.0.4
expo-updates@~57.0.25`), with the dependency policy rows, the shared module map and
  `tools/stack.json` in the same change. `npm run check:deps` passes and prints one `WARN` line per
  younger patch with its due date (from 2026-10-20: expo-crypto, expo-dev-client, expo-sharing,
  expo-splash-screen, expo-updates, jest-expo; 2026-10-22: expo-auth-session, expo-constants,
  expo-linking, expo-notifications; 2026-10-23: expo, expo-router), while plain `npx expo-doctor`
  and `npx expo install --check` exit 1 until then. On each due date the same command moves the next
  set (`npx expo install expo@~57.0.30` brings its map; jest-expo with `npm install -D`). Expo SDK 58
  became npm `latest` (58.0.14) on 2026-10-16; `check-sdk-trigger.mjs --online` says no move before
  2026-10-23T19:54Z.
- **AdMob sample app ids in every variant.** Without an app id the Google Mobile Ads SDK stops the app
  at launch; the harness never ships, so production uses Google's published sample ids too.
- **The app reads sample tasks from memory.** The data layer is opened, migrated, checkpointed and
  handed down (`useAppData()`), but the Tasks model keeps three sample tasks in state, so a fresh
  install shows something and the screen test stays a pure view test.
- **`test/test-app.tsx` stays the canonical tree** (services, react-intl with an empty catalog, the
  `language` and `direction` options with the text locale and the layout direction, a TanStack Query
  cache): it is drift-checked, so the harness cannot grow it with its catalogs and theme as its header
  asks an app to. `use-tasks-model.test.tsx` therefore wraps the real `I18nProvider` inside
  `createProvidersWrapper()` itself.
- **System font in a build.** The canonical `fonts.ts` names Noto Sans families, but no font file
  exists in the repository, so there is no `expo-font` entry; Jest and `expo export` do not need the
  files.
- **Typed routes are not generated** (`expo export` does not write `.expo/types`; only `expo start`
  does), so `Href` is a plain string in these checks.
- **The agent settings** (`.claude/settings.json`, canonical) take effect only when an agent is started
  inside `tools/harness`; their hooks call `git rev-parse --show-toplevel`, which here is this
  repository's root, so do not start an agent session inside the harness.

- **Agent files inside a sub-folder.** `AGENTS.md` and `CLAUDE.md` (expo-project-bootstrap) are
  here because check-skeleton requires them in every app. In this repository Claude Code also loads
  `tools/harness/CLAUDE.md` when an agent works on files in this folder; its rules are generic
  (start green, stop and ask, never bypass a hook) and agree with the library's own.
- **CI and EAS files are inert here.** GitHub reads only the repository root's `.github/`, so the
  adopted `.github/workflows/*` never run; `eas.json` and `scripts/eas/*` are never run against a
  real project (no `extra.eas.projectId`). `contracts/android-release.json` keeps the template's one
  permission (`INTERNET`): check-store-aab needs the real list from a release bundle, which a native
  round fills in (`contracts/android-emu-build.json` already holds the merged list of a 2026-10-14
  prebuild).
- **Root-wired kits plug into the skeleton's optional slots (owner decision, 2026-10-17).** Crash
  reporting, analytics, local and push notifications and, for test builds only, the debug kit and
  the parity kit are entries of the harness's registry (`src/services/create-root-kits.ts`); the
  root files stay canonical and byte-identical. Each kit is off by default (no DSN, no analytics
  vendor, no push server or accounts, no reminder rows, no approved parity frame), and a production
  build creates no test-only kit. Before the slots (2026-10-16) adopting crash reporting alone failed
  check-crash-reporting's `config-plugin`, `metro-debug-ids`, `consent-applied` and `sink-connected`.

  (no Expo Router) lacked it, so every route test, and every test that imports `expo-notifications`
  (which imports `expo-router`), failed with "Cannot use import statement outside a module".
- **`react-native-keyboard-controller` and `react-native-audio-api` crash on import in Jest**; both ship
  a JS mock, now handed to Jest by root mocks in `__mocks__/`.
- **`expo/types` still breaks `TextStyle` under React Native's Strict TypeScript API** (TS2353 on
  SDK 57.0.26). The root `tsconfig.json` lists `expo-env.d.ts` in `include` (so `expo start` has
  nothing to add to a gated file) and in `exclude` (so it never enters a program).
- **`tsBuildInfoFile: ${configDir}/node_modules/...`** would create `src/node_modules/` for the app
  program; `src/tsconfig.json` points its build info at the root cache.
- **expo-doctor fails a script named like a binary**: the source's `knip` script is `check:unused`.
- **jest-expo derives the `@/` mapper from `tsconfig.json` only in the working directory** (and not
  through `extends`), so `jest.config.js` spells out the aliases and the root `tsconfig.json` keeps
  `paths`.

Found while making the harness the reference app (reported to the owning skills, not yet fixed):

- **`process.env['X']` turns `any` in the root program once expo-modules-core's globals load** (any
  `expo-sqlite` import pulls them in): `@typescript-eslint/no-unsafe-argument` then fails an
  `app.config.ts` that passes one variable. Passing the whole `process.env` to `resolveAppVariant`
  (the canonical resolver) avoids it.
- **The forced Intl polyfills change Jest's number output** for a tag without `-u-nu-`
  (`new Intl.NumberFormat('ar-EG')` prints Latin digits under the polyfill, Arabic-Indic digits under
  Node's ICU), so a test that leans on Node's ICU fails as soon as `src/i18n/intl-polyfills.ts` exists.
- **Stryker needs the Worklets plugin for every file it did not mutate**: with the plugin off for
  the whole mutation run, a related screen test that renders `PressableSurface` threw
  (`[Reanimated] useAnimatedStyle was used without a dependency array or Babel plugin`), because
  Reanimated reads the plugin's closure when no dependency array is passed. With the plugin on for
  every file, a mutated file with a file-level `'worklet'` directive fails with
  `"stryNS_9fa48" is read-only`. The canonical `babel.config.js` therefore turns the plugins off
  only for the files that hold Stryker's namespace (both cases verified 2026-10-10).
- **fast-check's `fc.record` can build null-prototype objects**; a spread turns them into plain ones,
  which `toStrictEqual` then tells apart. Map records through `({ ...value })` in properties that
  compare a transformed copy.
- **knip reports `plutil` as an unlisted binary** in ios-simulator-build's `build-steps.ts` under the
  canonical knip.json; an app needs `ignoreBinaries: ["plutil"]` with its reason.
- **Template API that the template's own tests never import fails knip** in an app that adopts it
  without using it (motion-and-animation's `reducedEntering`, `reducedExiting`, `MomentId`); knip
  counts test imports, and typescript-and-lint-rules forbids knip ignores on app code.
- **expo-notifications writes `aps-environment: development` in every build** unless `mode` says
  otherwise; the native snapshot showed it in the production config.
- **expo-dev-client's plugin adds `NSLocalNetworkUsageDescription` and `NSBonjourServices` to the
  generated Info.plist of every variant** (visible in the production `contracts/native-config.json`).
  That is correct for SDK 57: the plugin's build phase `[Expo Dev Launcher] Strip Local Network Keys
for Release` removes `_expo._tcp` and the default description from every non-Debug product, and the
  dev-launcher and dev-menu pods are Debug-only (`debugOnly`), so no Release build carries them
  (ios-simulator-build, references/build-variants.md).

## Changing the harness

- **A canonical file changes:** edit it in `tools/shared/repo-templates/`, then run
  `node tools/verify-templates.mjs --sync-harness` and the proof commands above. Never edit the
  harness copy by hand: the drift check fails on it. A new file under `src/`, `test/`, `scripts/` or
  `design/` there is canonical at once; one under another folder needs a `CANONICAL_FILES` entry.
- **A finished skill changes a template the harness adopted:** run
  `node tools/verify-templates.mjs --sync-harness` (it refreshes every plain `adopted.json` entry),
  merge the change by hand into the adapted copies the drift check cannot guard, and rerun the proofs
  and that skill's checkers.
- **A skill is finished:** run each of its checkers against `tools/harness`; adopt the templates its
  checkers require (each copy goes into `adopted.json`, `adapted` with its reason when the harness
  changes it), wire them the way its workflow says, and add its rows to the checker table.
- **A version changes:** edit `tools/harness/package.json` (dev tools also in
  `tools/shared/repo-templates/package.json`), run `npm install --prefix tools/harness` (Expo modules:
  `npx expo install <pkg>` inside `tools/harness`), rerun every proof command, update `tools/stack.json`
  and `contracts/dependency-policy.json`, and commit `package.json` and `package-lock.json` together.
- **Expo SDK 58:** `npx expo install expo@^58.0.0 && npx expo install --fix` inside `tools/harness`,
  then `npx expo-doctor`, the proofs, and every skill's `verify-templates` run.
- **The app itself** stays neutral (Tasks): one feature, sample data, and the finished skills' layers
  wired the way an app adopts them.
