# ReactNative-Skills — house decisions

The binding decisions every skill in this repository follows. Contributors and the agents that build
the skills read this before touching a skill. When a skill and this file disagree, this file wins;
change it here first, then update the skills.

## 1. Purpose

A public, general-purpose library of agent skills for React Native apps built with Expo. Every
skill is **deep and self-verifying**: rules with reasons, a workflow, a definition of done that ends in
a zero-dependency checker printing `RESULT: PASS`, templates that compile in a real Expo app, and a
self-test that proves every checker catches the bugs it exists to catch (planted-bug fixtures).

The skills were generalized from a private production library (one Expo monorepo app). Their depth is
the point: generalize, never thin out. A rule that encoded that app's product decision is restated as a
general default (see §11), not deleted, and its checker keeps its teeth.

**Pinning policy** (`tools/stack.json` `policy`): versions are what `tools/harness` installs on the verified date under a
7-day minimum release age. Expo SDK runtime packages keep the `~` specifier `npx expo install` writes; dev tools in the
Expo map (typescript, jest, jest-expo) are pinned exactly inside Expo's range; everything outside the Expo map is pinned
exactly. Installs use npm ≥ 11.17 (`engine-strict`); CI needs Node 26 or `npm i -g npm@11.17.0`.

Expo SDK 58 is expected soon after 2026-10-03. Every version-sensitive fact carries a "verified on"
date and a re-verify command, so the move is a data refresh, not a rewrite.

## 3. Canonical app layout (single app first)

Skills, templates and checkers assume one Expo app at the repo root. Monorepo guidance is fenced under
a heading "When multi-package" and every checker accepts directory options for it.

```
<repo>/
  app.config.ts             the only app config (no app.json); reads APP_VARIANT
  eas.json                  build/submit/update profiles
  package.json  tsconfig.json  eslint.config.mjs  babel.config.js  jest.config.js  ...
  src/
    app/                    Expo Router routes ONLY: _layout.tsx, (group)/, [id].tsx, +not-found.tsx.
                            Route files are thin: they render a screen from src/features/.
    features/<feature>/     <feature>-screen.tsx (pure view) · use-<feature>-model.ts (the only code that
                            reads stores/services/navigation) · components/ · pure logic .ts · tests beside
    ui/                     shared presentational primitives (AppText, buttons, rows, dialogs, icons); ui/a11y/
    hooks/                  shared cross-feature hooks (use-is-app-active, use-window-class)
    theme/                  tokens, theme sets, ThemeProvider, makeStyles, motion
    core/                   pure domain: no React, React Native, Expo or Skia imports
    services/<concern>/     <concern>-port.ts · <library>-<concern>-adapter.ts · fake-<concern>.ts;
                            an optional kit's <concern>-root-kit.tsx; create-root-kits.ts (the kit registry)
    stores/                 Zustand stores, reducers, selectors
    data/                   SqlDriver, repositories, migrations, the save document (appendix)
    api/                    ApiClient, query keys, request/response schemas
    i18n/                   catalogs/<locale>.json, intl setup, polyfills, direction
    config/                 app-variant.ts, environment, feature flags
  test/                     test utilities (renderWithProviders), shared fixtures
  __mocks__/                root mocks for native modules
  scripts/                  Node tooling (.ts run by Node type stripping, or .mjs)
  .maestro/                 E2E flows
  contracts/                repo-owned JSON contracts read by the skills' checkers (see §6)
```

- Path aliases: `@/*` → `./src/*` (the Expo template default) and `@test/*` → `./test/*` (src tests reach the root
  test helpers only through it). Relative imports only between siblings; parent-relative imports are banned.
- Two TypeScript programs: the root `tsconfig.json` (whole repo, types `jest` + `node`) and `src/tsconfig.json` (app
  code, types `jest` only — no Node globals in the app; `src/app-env.d.ts` declares `process` for `EXPO_PUBLIC_*`,
  declared in `src/env.d.ts`). `npm run typecheck` runs both.
- Fixed homes the lint zones, coverage and Stryker are pathed to: `src/core/rng/` and `src/core/dates/` (seeded
  determinism), `src/games/<game-id>/{rules,levels,sim,geom}/` (the games plugin), and the shared real-time and
  geometry kit `src/core/realtime/` and `src/core/geom/` (realtime-game-loop).
- Named exports everywhere except where a tool requires a default export (Expo Router route files,
  `app.config.ts`, config plugins).
- When multi-package: npm workspaces `apps/*` + `packages/*`, package scope `@<org>/<pkg>`, TS-source
  packages. Checkers find workspaces from `package.json` `workspaces`, never from hard-coded folders.

## 5. The skill standard

`CONTRIBUTING.md` is the full standard; `tools/standard.json` holds its constants and
`tools/validate-skills.mjs` enforces the checkable parts. In short:

- **Frontmatter:** `---` on line 1; one-line YAML values only; `name` (= folder) and `description`;
  `disable-model-invocation: true` only for side-effecting `run-*` runbooks that contain a stop-and-ask
  step; `metadata` allowed; never `allowed-tools`.
- **Description:** third person, starts with a verb, ≤ 300 characters (aim ≤ 250), "Use when …" with
  concrete trigger words, "Not for … (other-skill)". No `<`/`>`. Never "I"/"you".
- **SKILL.md ≤ 300 lines, this section order:** `# Title` + what the skill makes true · `## Rules that
  must hold` (numbered, testable, each with its why) · `## Workflow` (which reference to read, which
  template to copy, which script to run, at which step) · `## Definition of done` (checklist ending in
  `node ${CLAUDE_SKILL_DIR}/scripts/<check>.mjs <args>` prints `RESULT: PASS`) · `## Anti-patterns` ·
  `## Files in this skill` (every file, with when to read/run it) · `## Related skills` (names only).
  Rules and the definition of done sit at the top because only a skill's first ~5,000 tokens survive
  context compaction.
- **Self-contained:** a skill never points at files outside its folder (no repo docs, no `tools/`, no
  other skill's files, no absolute or `../` paths). It carries copies of what it needs. Another skill
  may be *named* for a hand-off, never depended on. Paths the skill creates or checks in the user's app
  repo (`src/features/...`) are content, not dependencies.
- **Folders:** `references/` (knowledge read on demand; ToC when > 100 lines) · `templates/` (real files
  copied into the app; line 1 names the repo path; `__UPPER_SNAKE__` placeholders) · `examples/`
  (shapes to imitate, never copied) · `scripts/` (checkers) · `tests/fixtures/` · `assets/` (data).
- **Writing:** calm, explain why, one default not a menu, prescriptive where work is fragile, flexible
  where judgement matters. Say plainly what a human must do by hand; stop and ask before anything
  irreversible or outward-facing (store uploads, deleting data, spending money, publishing).
- `${CLAUDE_SKILL_DIR}` means "the folder that contains this SKILL.md". Agents that do not expand it
  substitute that path (stated once in AGENTS.md and README).

## 6. Scripts and check-lib

- Node ESM `.mjs`, Node ≥ 22, **zero dependencies** (`node:` built-ins only). A skill that truly needs
  packages (Playwright, image diff) ships a pinned `scripts/package.json` + lock and accepts
  `--tooling <dir>` (installs default to `<repo>/.skill-tooling/<skill>`, git-ignored).
- Invocation: `node ${CLAUDE_SKILL_DIR}/scripts/<name>.mjs [repo-root] [options]` — the repo root is an
  optional **positional** argument (default `.`), never `--root`. `--help` prints usage.
- Exit `0` pass · `1` problems found · `2` bad input or environment. Last line always `RESULT: PASS` or
  `RESULT: FAIL (<n> problems)`. Each problem line names file:line, the rule id, and the fix.
- Nothing to check (missing target) → exit 2, never a silent pass. A target that should exist by now
  → a problem (exit 1).
- **SKIP** (`report.skip`) only for a rule whose target is legitimately not created yet in an app being
  adopted incrementally: `notYetCreated(root, { file, owner })` → `SKIP <file> [<rule>] not yet created
  (<owner> creates it)`. **NOT APPLICABLE** (`report.notApplicable('<repo fact>')`, exit 0) when a repo
  fact proves the whole check does not apply (for example, `react-native-google-mobile-ads` is not in
  `package.json`). Ship gates (release, store-artifact, completeness) never skip; their only relaxation
  is `--rehearsal` (keyless dry run), which skips only the signing rule and prints `REHEARSAL: not a
  release gate` first.
- **Layout and config:** every checker resolves paths through check-lib's `resolveLayout(root)`: the
  §3 defaults, `tsconfig.json` `paths` aliases, `package.json` `workspaces`, overridable by an optional
  repo file `rn-skills.config.json` and by per-script options. A key is documented in the skill that
  reads it.
- **Contract files:** where a checker needs app-specific facts (screens and their testIDs, settings
  fields, contrast pairs, navigation groups, perf budgets), it reads a repo-owned JSON contract in
  `contracts/<name>.json` (a template ships in the skill). Checkers stay strict; the facts belong to the
  app.
- **Repo scans** use `walkRepo(root)` (REPO_SCAN_IGNORES + each workspace's output folders from `package.json` +
  pruning any folder containing a `SKILL.md`) (installed skills live in `.agents/skills`, `.claude/skills`, `.cursor/…` and must never be
  scanned). Each scanning checker has a fixture with planted findings under `.agents/skills/` and
  `skills/` that must stay silent.
- **No runtime env coupling** (`no-runtime-env` rule): never `CLAUDE_PLUGIN_ROOT`, `CLAUDE_PROJECT_DIR`,
  `CLAUDE_PLUGIN_DATA`, `CLAUDE_ENV_FILE`, and no script reads `CLAUDE_*` from `process.env`.
- **Devices are always named:** every `maestro` call passes `--device <id>`; `xcrun simctl` targets a
  UDID (never `booted`/`all`); `xcodebuild -destination id=<udid>`; `adb -s <serial>`; emulators by AVD
  name. Tools name their simulators `<project>-<purpose>`. The allowed device-binding helper names
  (`maestroGlobalArgs`, `adbArgs`, `adbDeviceArgs`, …) are data in `tools/standard.json` (`device.bindingHelpers`).

## 7. Self-test fixtures

`scripts/selftest.mjs` calls check-lib's `runSelftest` over `tests/fixtures/`. Case kinds:
`good/` (exit 0, `RESULT: PASS`) · `pass-<case>/` (exit 0 + every line of `EXPECT.txt`) · `bad-<case>/`
(exit 1 + every line of `EXPECT.txt`; at least one per suite; one planted bug per rule) ·
`error-<case>/` (exit 2 + `EXPECT.txt`). In an overlay suite `ARGS.txt` replaces the suite arguments for every case
kind (suites not yet converted keep the old error-only rule).

**Overlay format (the default):** a suite declares its base in `SUITE.json` (keys `base`, `extends`, `ops`,
`argsFile`, `renames`; `legacyOps` only while migrating an old assembler) or with a `base/` folder; bases can be
`tests/bases/<name>/`, the skill's `templates/`, or `good/`. A case folder holds `EXPECT.txt` plus `mutation.json`
(ordered ops: `replace`, `json` set/delete, `write`, `delete`, `rename`, `png`, `copy`, `mkdir`, `plant`; the list is
check-lib's `OVERLAY_OPS`, mirrored in `standard.json`) and/or files under the case's `overlay/` folder and
`DELETE.txt`; `plant.json` writes content that must never be committed as-is (defused secrets). **One file per case:** a
suite may keep every case's ops (and its `ARGS.txt` words as `"args"`) in one suite-level `CASES.json`
(`{ "<case>": [ops] | { "expect": [...], "ops": [...], "args": "...", "base", "extends" } }`). With `"expect"`
(the `EXPECT.txt` lines) the entry is the whole case and needs no case folder; without it the key names a
case folder that holds only its `EXPECT.txt`. A case never has both an entry and its own
`mutation.json`/`ARGS.txt`, nor both `"expect"` and `EXPECT.txt`, and a key without `"expect"` must name a case
folder (all fail loudly). One entry with `"expect"` is the preferred form for new and repacked suites (repo
file budget: `node tools/fixtures-pack.mjs <skill-dir> --expect --verify`); only a base layer, a case with a
large binary overlay file and `good/` keep folders. A `replace` find
string must occur exactly once unless the op says `all`, `count` or `occurrence`. runSelftest assembles each case
into a temp folder; every op must apply, so a stale fixture fails loudly. `--materialize <dir>` writes assembled
cases for inspection; `--case <name>` runs one.

Hygiene: no file or folder named `.gitignore`, `metadata.json`, `.git`, `__pycache__` inside a skill
(use `dot-gitignore`; assembly renames it). Planted secrets are stored defused and assembled at run
time (push protection). Budget: `tests/` ≤ 1 MB and ≤ 600 files per skill; any file anywhere in a skill ≤ 256 KB;
binaries only from the allow-list in `standard.json` (images, fonts, audio, pdf, and small binary `.plist` /
`.jsbundle` / `.hbc` audit inputs). PNGs are generated by `writePng`, not committed, except a few reviewed goldens.
The repo budget (`tools/check-repo-hygiene.mjs`) counts unique content, so synced copies count once. Its limits (`standard.json`
`repo`) are 30 MB of unique content and 8,000 files: owner decision (b) of 2026-10-17 shrank fixtures first
(every case moved into its suite's `CASES.json` with its `"expect"` lines, 13,367 -> 7,461 files, no planted-bug
case lost, every assembled case byte-identical and every self-test outcome identical), then set the byte limit
about 5% above the measured 28.7 MB of real content (scripts, references, templates, the harness lockfile).

## 8. Templates and the harness

`tools/harness/` is the reference Expo SDK 57 app (Expo Router template + the canonical stack + the
canonical root configs). `node tools/verify-templates.mjs <skill>` copies a skill's templates into a
temp copy of the harness at the paths their first line names, then runs `tsc --noEmit`, ESLint
`--max-warnings 0`, and the copied Jest tests. A template that does not pass there does not ship.
A template that lands on a harness copy `adopted.json` marks adapted from it, where that copy holds every line of the template (the harness's test-only entry adds other skills' members), leaves the copy in place, so the template's lines compile inside it and the harness code that reads the extra lines still compiles. Templates are complete, real files; examples are shapes only.

## 10. Vocabulary and neutral domains

- Write for the developer and the reviewer ("the reviewer reads the report first"), about "the app".
  Spec references are the app's own spec IDs; a later build step is "not yet created"; designs are
  the app's design system and the approved design baseline; locales are the app's locales (examples
  use `en` + an RTL locale, e.g. `ar`); tool-made names are `<project>-<purpose>`; imports use `@/…`
  (single app) or `@<org>/<pkg>` (fenced). No name, path or term of the source app appears.
- Example domain for core skills: a **Tasks** app (tasks, lists, reminders, a Premium entitlement).
  Other neutral nouns: Note, Product, Order, Account. Never a real app's nouns. Games examples use
  public-domain mechanics (Lights Out as `lights-out`, a sliding puzzle, a simple arena chase).

## 12. Platforms

next to VoiceOver, `adb` next to `simctl`, Play next to App Store, edge-to-edge and predictive back,
Android permissions and channels). Facts verified only on one platform are marked as such.

The web is an opt-in third target (web-support). The expo-project-bootstrap skeleton and the harness set
`platforms: ['ios', 'android']` in `app.config.ts`, so web-support's checkers print NOT APPLICABLE there; an
app that ships the web adds `'web'` together with web-support's contract, headers and storage gate.

## 13. Catalog and plugins

`tools/catalog.json` is the single source for categories, the plugin each skill belongs to (`core` or
`games`), priority and manual-only flags. `tools/build-catalog.mjs` writes README tables, the AGENTS.md
intent map, `skills.json`, `docs/skills-data.js` and the two plugin entries in
`.claude-plugin/marketplace.json` (each entry lists its `skills`, which replaces the default scan).
The index skill (`react-native-conventions-index`) renders its own task table from
`skills/react-native-conventions-index/assets/index.json`. Never edit generated output by hand.

Namespaces (verified 2026-10-17 with `claude plugin install` from a local copy of the marketplace and `claude plugin
details`): there is **no** `.claude-plugin/plugin.json`. Both entries use `source: "./"`, and a root `plugin.json` would
name both plugins (its name wins over each entry's), so the games skills would load as `react-native:<skill>`. Each
marketplace entry carries its own metadata instead (version, author, homepage, repository, license, keywords, written by
build-catalog from `PLUGIN_META`), so skills load as `react-native:<skill>` and `react-native-games:<skill>`;
build-catalog fails on a root `plugin.json` (`plugin-json-present`) and `tools/tests/plugin-manifests.test.mjs` checks
the manifests against the catalogue. Codex reads one manifest (`.codex-plugin/plugin.json`, `skills: "./skills/"`), so
the Codex plugin ships every skill, games included.

Listing budget: Claude Code lists skill names + descriptions within ~1% of the context window. Keep
descriptions ≤ 250 characters on average; `check-skill-set` enforces a set budget of 20,000 characters for the
listed skills at the default `skillListingBudgetFraction` 0.01, and CI runs it on every change.

## 14. Relationship to Expo's official skills

Expo publishes official skills (`expo/skills`: expo-router, eas-app-stores, eas-update, expo-ui,
expo-data-fetching, …) that teach Expo APIs. This library is complementary: it enforces engineering
rules and proves them with checkers. Never reuse an Expo skill name (`tools/standard.json` reserves all
24, verified 2026-10-16). Where an Expo skill is the better API reference, name it as a hand-off in
Related skills: "- Expo's `<expo-skill>` skill - ..." or "- `<expo-skill>` - (Expo's official skill) ..."
(CONTRIBUTING; skill-maintenance's check-skill accepts both for the reserved names only).
